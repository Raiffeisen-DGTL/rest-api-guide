# CLAUDE.md — Spectral Rulesets Project

## Что это за проект

Spectral-линтер для OpenAPI/AsyncAPI спецификаций. Правила используются для валидации API документации по внутреннему API Guide Raiffeisen.

Зависимости устанавливаются через `npm install`. Запуск тестов: `npm test`.

## Структура

```
rules/openapi/      ← исходные файлы правил (по одному на правило)
rules/asyncapi/
functions/          ← кастомные JS-функции для сложной логики
functions/utils/    ← хелперы (refResolver, traverse, isObject, …)
tests/openapi/      ← тесты (один .test.ts на правило)
tests/utils/        ← setupSpectral(), retrieveDocument(), Severity enum
*-ruleset.yaml      ← AUTOGENERATED, не редактировать вручную
```

## Как добавить новое правило

### 1. Файл правила `rules/openapi/<rule-name>.yaml`

```yaml
x-rulesets: [ base ]          # base | documentation | required | ai-ready
functions:
  - myFunctionName             # только если нужна кастомная функция
functionsDir: "../../functions"
rules:
  rule-name-in-kebab-case:
    description: Описание правила (обычно на русском)
    documentationUrl: https://gitlabci.raiffeisen.ru/cib/api-guide/-/tree/master/spectral/rules/openapi?ref_type=heads#rule-name
    severity: error            # error | warn | info | hint
    message: "{{error}}"       # ОБЯЗАТЕЛЬНО при кастомной функции — иначе сообщения функции заменяются на description
    given: "$"                 # JSONPath
    then:
      function: myFunctionName
```

**Важно:** если функция возвращает собственные сообщения об ошибках, в правиле обязательно нужно указать `message: "{{error}}"` — без этого Spectral подставит `description` вместо сообщений функции.

### 2. Кастомная функция `functions/<camelCaseName>.js`

```js
'use strict'
import { createRulesetFunction } from '@stoplight/spectral-core'

export default createRulesetFunction(
  {
    input: { type: 'object' },  // JSON Schema для входного значения
    options: null,               // null если functionOptions не нужны
  },
  function myFunctionName(input) {
    const errors = []
    // ... логика ...
    errors.push({
      message: 'Текст ошибки',
      path: ['paths', '/v1/foo', 'get', 'responses', '400'],
    })
    return errors  // [] = нет ошибок
  },
)
```

- Неиспользуемые параметры `opts`, `context` можно опустить из сигнатуры
- `context.path` — текущий JSONPath (массив строк), удобно для составления path ошибки
- `context.document.formats` — для проверки версии OAS (`oas3`, `oas3_0`, `oas3_1`)
- `resolveRef(ref, context)` из `./utils/refResolver.js` — для ручного разрешения `$ref` (только при `resolved: false`)

### resolved vs unresolved

| `resolved: false` в YAML | Поведение |
|---|---|
| не указано (по умолчанию) | Все `$ref` раскрыты до вызова функции. Функция видит итоговую схему. |
| `resolved: false` | Функция видит сырые `$ref`. Нужно для правил, которые проверяют **наличие** `$ref` (например, `methodRequestResponseComponents`). |

### 3. Тест `tests/openapi/<rule-name>.test.ts`

```ts
import { setupSpectral } from '../utils/utils'
import { Spectral } from '@stoplight/spectral-core'
import { Severity } from '../utils/severity'

let linter: Spectral

describe('Rule Name Tests', () => {
  beforeAll(async () => {
    linter = await setupSpectral('./rules/openapi/rule-name.yaml')
  })

  test('valid case', async () => {
    const results = await linter.run({ openapi: '3.0.3', info: {...}, paths: {...} })
    expect(results.length).toBe(0)
  })

  test('invalid case', async () => {
    const results = await linter.run({ ... })
    expect(results.length).toBe(1)
    expect(results[0].message).toBe('Текст ошибки')
    expect(results[0].severity).toBe(Severity.error)
    expect(results[0].path.join('.')).toContain('paths./v1/foo')
  })
})
```

Для тестов с внешними файлами (`$ref` на файлы) использовать `retrieveDocument(filePath)` и класть фикстуры в `tests/openapi/testData/<ruleName>/`.

### Severity enum
```
Severity.error   = 0
Severity.warning = 1
Severity.info    = 2
Severity.hint    = 3
```

## Генерация рулсетов

Не запускать вручную — Husky делает это автоматически при коммите:
```bash
node ./build-rulesets.js
```
Скрипт читает все `rules/**/*.yaml`, группирует по `x-rulesets` и генерирует `*-ruleset.yaml`.

## Уже реализованные правила (примеры для справки)

| Файл правила | Функция | Что проверяет |
|---|---|---|
| `method-request-response-components.yaml` | `methodRequestResponseComponents.js` | Тела запросов/ответов вынесены в `$components` |
| `object-request-response-postfix.yaml` | `objectRequestResponsePostfix.js` | Схемы запросов/ответов с постфиксами Request/Response |
| `operation-success-response.yaml` | `oasOpSuccessResponse.js` | Наличие 2xx/3xx ответа у операции |
| `response-error-structure.yaml` | `responseErrorStructure.js` | Структура ошибочных ответов (4xx/5xx): `error.code`, `error.message` |

## Частые ошибки

- **Сообщения функции не показываются** → добавить `message: "{{error}}"` в YAML правила
- **Тест не находит правило** → путь в `setupSpectral()` должен быть относительным от корня проекта (`./rules/openapi/...`)
- **`$ref` не разрешаются в тестах с inline объектами** → это нормально, resolved mode работает только при наличии `components` секции в документе
